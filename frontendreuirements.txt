TraceX Frontend Design Plan

Overview

The TraceX frontend should be designed as an investigation workflow platform, not as a collection of dashboards or feature pages. Every screen should guide an investigator through the natural AML investigation process instead of requiring them to navigate between different modules like Graphs, Timeline, Transactions, Evidence, or AI.

The entire user experience should revolve around one simple flow:

Dashboard → Investigation Workspace → My Center

The investigator should spend almost all of their time inside the Investigation Workspace. Once a case is opened, they should never have to leave it to access graphs, timelines, evidence, AI, reports, or transactions. Everything needed for that stage of the investigation should already be available within the current workspace.

The interface should be clean, spacious, modern, and minimal. Every page should have a single purpose, and every feature should exist only where it is needed.

⸻

Overall Navigation

The application should have a permanent top navigation bar containing only three primary pages.

1. Dashboard

Purpose:
View all incoming alerts and overall system status.

⸻

2. Investigation Workspace

Purpose:
Investigate assigned alerts from start to finish.

⸻

3. My Center

Purpose:
Manage monitored accounts and view personal audit history.

⸻

No additional top-level pages should exist.

There should not be separate pages for Graphs, Timeline, Transactions, AI, Evidence, Rules, Reports, Analytics, or Customer Profiles. These should all appear naturally inside the investigation workflow.

⸻

Dashboard

The Dashboard acts as the landing page after login.

Its purpose is to give investigators and administrators a quick understanding of the current alert landscape and allow them to begin investigations.

No investigation should occur on this page.

⸻

Analytics Summary

At the top of the page, display a compact row of summary cards showing the current state of the system.

Suggested cards include:

* Total Active Alerts
* Critical Alerts
* Open Cases
* Average Risk Score

These cards are intended only for quick awareness and should remain compact.

⸻

Trend Visualizations

Below the summary cards, display one or two simple charts.

Examples:

* Alerts over time
* Alert distribution by severity

The charts should provide quick visual context but should not dominate the page.

⸻

Alert Table

The primary component of the Dashboard is a searchable and filterable table listing all alerts.

Each row should display:

* Alert ID
* Account
* Alert Type / Typology
* Risk Score
* Priority
* Generated Time
* Current Status
* Assigned Investigator

Each alert should have an action allowing it to be opened in the Investigation Workspace.

⸻

Administrator Actions

When viewed by an administrator, the alert table should include additional controls:

* Assign Investigator
* Reassign Investigator
* Bulk Assignment

Administrators should also be able to filter alerts by investigator workload.

⸻

Investigator View

Investigators cannot assign alerts.

They simply open alerts assigned to them.

⸻

Investigation Workspace

The Investigation Workspace is the core of TraceX.

Almost every interaction performed by an investigator happens here.

Instead of opening investigations in separate browser pages, every investigation should open as a horizontal case tab.

Example:

Case 102 | Case 245 | Case 418 | +

This allows investigators to work on multiple investigations simultaneously.

Each case should preserve its complete state independently.

Switching between case tabs should restore:

* Scroll position
* Expanded graph
* Selected transactions
* Applied filters
* Notes
* Investigation progress

Nothing should reset when changing tabs.

⸻

Case Status

Each case tab should clearly indicate its current investigation stage.

Possible stages include:

* Triage
* Deep Investigation
* Monitoring
* Closed

The stage should always be visible without opening the case.

⸻

Triage Workspace

Every newly opened alert begins in the Triage workspace.

The objective of Triage is to help the investigator quickly determine whether the alert is a false positive or requires a deeper investigation.

Only essential information should be shown.

The page should remain concise and easy to scan.

⸻

Section 1 – Alert Summary

Display all important alert information.

Include:

* Alert ID
* Alert Type
* Detection Rule
* Priority
* Risk Score
* Time Generated
* Current Status

⸻

Section 2 – AI Alert Summary

Provide a short explanation generated by the system describing why the alert was created.

This should be one of the first sections visible because it immediately gives investigators context.

⸻

Section 3 – Customer Snapshot

Display key customer information.

Include:

* Customer Name
* Customer Type
* Risk Category
* KYC Status
* Geographic Risk
* Occupation
* Previous Risk Level

Only the most relevant information should be shown.

⸻

Section 4 – Simplified Money Flow

Display a small simplified graph highlighting the primary flow of suspicious funds.

This graph is intended only to provide quick understanding.

It should not contain advanced graph interactions.

⸻

Section 5 – Transaction Summary

Provide a concise overview of suspicious activity.

Examples include:

* Number of Transactions
* Total Amount
* Largest Transaction
* Most Frequent Destination
* Average Transaction Value

⸻

Section 6 – Previous Investigation History

Display historical information related to the account.

Include:

* Previous Alerts
* Previous False Positives
* Previous STRs
* Existing Monitoring Status

⸻

Section 7 – Network Risk

Present a summarized network risk score together with a brief explanation of why the network received that score.

⸻

Section 8 – AI Recommendation

Display suggested next investigative actions.

Examples:

* Escalate for deeper investigation
* Review connected beneficiaries
* Examine rapid fund movement

Recommendations are advisory only.

⸻

Section 9 – Investigator Notes

Provide a notes section where investigators can record observations.

Notes should save automatically.

⸻

Section 10 – Decision Panel

The Triage workspace concludes with the investigator’s decision.

Available actions:

* Mark False Positive
* Continue to Deep Investigation

If False Positive is selected, investigator feedback explaining the reason must be mandatory.

Submitting either action should immediately:

* Update the case status
* Record an audit log entry

⸻

Transition to Deep Investigation

Selecting Continue to Deep Investigation should not create another case or another browser page.

The existing case remains open.

The workspace simply switches from the Triage view to the Deep Investigation view.

The case status changes from:

Triage

to

Deep Investigation

This transition should automatically be logged.

⸻

Deep Investigation Workspace

The Deep Investigation workspace is designed for comprehensive analysis.

Unlike Triage, it exposes all advanced investigation capabilities.

The investigator remains inside the same case.

⸻

Collapsible Triage Summary

At the very top of the page, display a collapsible summary of the completed Triage stage.

This allows investigators to quickly revisit initial findings without leaving the current workspace.

The summary should include:

* Alert Summary
* AI Summary
* Customer Snapshot
* Initial Decision
* Escalation Reason

⸻

Relationship Explorer

Display relationships between entities involved in the investigation.

Support relationships between:

* Accounts
* Customers
* Devices
* Shared Identifiers
* Beneficiaries

⸻

Complete Investigation Graph

Provide the complete interactive investigation graph.

Support:

* Node expansion
* Graph navigation
* Path highlighting
* Graph filtering

⸻

Investigation Timeline

Display the sequence of events chronologically.

Selecting a timeline event should highlight the corresponding transactions or graph entities.

⸻

Transaction Explorer

Display the complete transaction history.

Support:

* Search
* Sorting
* Filtering
* Transaction inspection

⸻

Similar Historical Cases

Show previously investigated cases with similar patterns.

Each result should display:

* Similarity Score
* Investigation Outcome
* Brief Summary

⸻

Evidence Management

Allow investigators to:

* Bookmark transactions
* Save graph paths
* Add investigation evidence
* Organize findings

⸻

AI Investigation Copilot

Embed an AI assistant within the investigation page.

The Copilot should answer questions related only to the currently opened investigation.

It should never open as a separate page.

⸻

Investigation Narrative

Display a generated investigation report.

Investigators should be able to review and edit the narrative before submission.

⸻

Investigator Notes

Continue using the same notes section from Triage.

Notes should persist throughout the entire investigation lifecycle.

⸻

Final Decision Panel

At the bottom of the investigation, present the final available actions.

Possible outcomes include:

* Mark False Positive
* Place Under Monitoring
* Escalate to Compliance / Generate STR
* Close Case

Every decision must require investigator feedback.

Submitting a decision automatically:

* Updates case status
* Creates audit log entry
* Triggers backend workflows

⸻

My Center

The My Center page contains investigator-specific information.

It should contain only two sections.

⸻

Monitoring

Display every account or network currently being monitored by the investigator.

Each monitored item should display:

* Account / Network Name
* Monitoring Reason
* Date Added
* Current Risk
* Latest Activity

A notification badge should appear beside the Monitoring section whenever new alerts are generated for monitored entities.

Example:

Monitoring (3)

Selecting a monitored entity opens its monitoring details, including:

* Monitoring history
* Original monitoring reason
* Related alerts
* Current investigation status

⸻

Audit Logs

Display a searchable timeline of every important action performed by the investigator.

Examples include:

* Opened Case
* Escalated Investigation
* Added Notes
* Added Evidence
* Generated AI Narrative
* Marked False Positive
* Started Monitoring
* Closed Case

Each entry should contain:

* Timestamp
* Case ID
* Action
* Investigator
* Additional Details

Filtering and searching should be supported.

⸻

Notifications

A notification icon should be available in the application header.

Notifications should inform investigators about events requiring attention.

Examples include:

* New case assigned
* Monitoring hit detected
* Case commented on
* STR generation completed
* Case reassigned

Notifications should never interrupt ongoing investigations.

⸻

General User Experience Principles

The interface should prioritize workflow over features.

Information should be revealed progressively, showing only what is necessary for the current investigation stage.

Navigation should remain extremely shallow with only three primary pages.

The investigator should never need to search for tools. Every tool should appear naturally within the workflow where it is required.

The Triage workspace should support fast decision-making with minimal cognitive load.

The Deep Investigation workspace should provide comprehensive investigative capabilities without requiring navigation to additional pages.

Every investigator action should immediately update the case state and automatically generate an audit log.

The design should feel like a guided investigation process rather than a collection of independent screens, ensuring investigators can move seamlessly from receiving an alert to completing an investigation with minimal clicks and maximum clarity.
